# ADR-0006: 모듈 과분해(over-decomposition) 재평가

## 상태

Accepted

## 날짜

2026-06-10

## 맥락

[ADR-0003](0003-module-decomposition-criteria.md)이 모듈 분리 기준을 정했지만, 초기 아키텍처
리뷰(ROADMAP 6.3)는 24개 모듈이 **과분해**일 수 있다고 지적했다 — 특히 파일 수가 적은
`media`·`review`·`notification` 등을 단독 모듈로 두는 것이 정당한지 재검토가 필요했다.

### 문제 정의

작은 모듈이 너무 많으면 빌드 그래프·인지 부하·보일러플레이트(작은 모듈도 3계층+포트 강제)가
비용이 된다. 이 비용이 경계 명확성의 이득을 넘어서는 모듈이 있는가? 있다면 인접 모듈로 통합해야 한다.

## 결정

**현재 모듈 분해를 유지한다.** 실측 분석 결과 명백히 통합이 정당한 모듈이 없으며, 통합은
오히려 (a) 기술 관심사 혼합(infra-*) 또는 (b) 별개 바운디드 컨텍스트 병합(도메인)을 초래해
득보다 실이 크다. 다만 통합을 재고할 **구체적 트리거**를 명시해 둔다.

### 분석 (2026-06-10 실측)

모듈 main 소스 파일 수:

| 구간 | 모듈(파일 수) |
|------|---------------|
| 기술 인프라 | redis(1)·s3(1)·observability(2)·persistence(2)·kafka(9) |
| 공유 | audit(6)·event(6)·common(7) |
| 조립 | app(8) |
| 보안 | security(9) |
| 소형 도메인 | review(15)·price(16)·service-availability(16)·media(17)·laundromat(18) |
| 중대형 도메인 | delivery(20)·geo(23)·operation(26)·notification(29)·order(30)·dispatch(31)·payment(31)·user(44) |

의존 그래프: 모든 도메인 모듈은 `common`/`event`/필요한 `infra-*` 만 의존하고 **도메인↔도메인
직접 의존이 0**이며, `carry-app` 만 전체를 조립한다([ADR-0003] 준수).

### 왜 통합하지 않는가

1. **박형 infra-* 모듈(redis·s3·observability·persistence)은 선택적 의존을 가능케 한다.**
   `carry-geo` 는 `infra-redis` 만, `carry-media` 는 `infra-s3` 만 의존한다. 이들을 단일
   `carry-infra` 로 합치면 모든 소비자가 불필요한 기술 의존(AWS SDK, Redis 클라이언트 등)을
   전이로 끌어오게 된다. 작은 파일 수는 "응집된 얇은 어댑터"의 결과이지 과분해가 아니다.

2. **소형 도메인 모듈은 각각 독립 바운디드 컨텍스트다.** `review`(배달 후 리뷰)·`price`(가격
   정책)·`service-availability`(지역·시간 가용성)·`media`(파일 업로드)는 서로 다른 비즈니스
   능력이고, 이벤트/쿼리 포트로만 통신한다. 인접 통합 시 한 모듈이 두 컨텍스트를 떠안아
   [ADR-0003]의 "비즈니스 능력 = 모듈 경계" 원칙이 깨진다.

3. **보일러플레이트 비용은 일관성의 대가로 의도된 것이다.** 작은 모듈도 3계층+포트를 갖는 건
   ArchUnit으로 강제되는 구조적 일관성의 결과이며, 새 기능·새 모듈이 같은 형태를 따르게 한다.

### 통합을 재고할 트리거

- 두 모듈이 **항상 함께 변경**되고(커밋 커플링) 한쪽이 독립적 의미를 잃을 때.
- 한 모듈이 단순 CRUD뿐이고 **고유 도메인 규칙·이벤트가 0**으로 수렴할 때(예: 향후 `media` 가
  순수 파일 패스 저장소로만 남으면 `common`/공유 유틸로 흡수 검토).
- 빌드 시간이 모듈 수로 인해 실측상 병목이 될 때(→ [ADR 미정] 빌드 성능 작업과 함께 판단).

## 결과

### 긍정적

- 경계 명확성·선택적 의존·구조 일관성을 그대로 유지.
- "과분해 우려"를 데이터로 점검하고 결론을 남겨, 다음 재평가가 이 기준선에서 출발한다.

### 부정적

- 모듈 수(24)로 인한 인지 부하·빌드 그래프 복잡도는 유지된다(트리거 충족 전까지 감수).

## 고려한 대안

### infra-* 모듈을 단일 carry-infra 로 통합

**기각**: 선택적 기술 의존이 깨져 모든 소비자가 불필요한 의존을 전이로 끌어옴.

### 소형 도메인(review/media 등)을 인접 도메인에 흡수

**기각**: 별개 바운디드 컨텍스트 병합 → 경계 침식. 파일 수가 적은 것은 도메인이 작은 것이지
잘못 분리된 것이 아니다.
